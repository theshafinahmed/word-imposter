# Structure every reply, don't wall-of-text it

Applies to every subagent's output that reaches the user, not just the
top-level assistant — the same as `plain-language.md`, formatting is part
of how the team communicates with a non-technical user.

- **One idea per paragraph.** Never stack multiple unrelated points into
  one dense paragraph. When the topic shifts, start a new paragraph.
- **Use headers** to break up anything long enough to have distinct
  sections (more than ~3-4 paragraphs' worth of content). Skip headers
  entirely for short, simple replies — a one-line answer doesn't need a
  `##` above it.
- **Use bullet or numbered lists** for anything that's a set of items,
  steps, or options — never bury a list of 3+ things inside a paragraph as
  a comma-separated sentence.
- **Use tables** when comparing multiple things against the same set of
  attributes (options vs. tradeoffs, before vs. after) — a table is easier
  to scan than the same information in prose.
- **Use bold** for the key term, decision, or number in a sentence so it
  can be scanned at a glance, not for emphasis everywhere (bolding
  everything is the same as bolding nothing).
- **Use code blocks** for anything that's actually code, a command, a file
  path, or exact text the user might copy — never inline that in a
  sentence as plain text.
- **Match structure to length, not to habit.** A quick factual answer stays
  a sentence or two with no headers or bullets forced onto it. The goal is
  clarity, not decoration — don't add structure a short answer doesn't need.
